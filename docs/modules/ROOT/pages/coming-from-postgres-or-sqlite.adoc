= Coming from Postgres or SQLite
:description: ArcadeDB SQL has no JOIN. See common join patterns rewritten with links, edges, MATCH, TRAVERSE and subqueries, with openCypher equivalents.

ArcadeDB's SQL is its own dialect. It is document-oriented and it has no `JOIN`: records point at other records by record ID, and a query follows those pointers. If you know Postgres or SQLite, most of `SELECT`, `WHERE`, `GROUP BY`, `ORDER BY` and `LIMIT` will look familiar. Relationships are where you change habits.

* A foreign key becomes a *link property*, a column that holds the record ID of another record. You read through it with a dot: `customer.name`.
* A join table, or a relationship you walk in both directions, becomes an *edge*. An edge is a record of its own, so it can carry columns such as a quantity.
* A recursive CTE becomes `TRAVERSE` or `MATCH` with a depth.
* openCypher works on the same data, and for relationships it is often the shortest way to say it.

Every script on this page ran against the published `{pkg-name}` 26.10.2.post1 wheel, and every output is what it printed. Rows come back as dictionaries, and the order of an unsorted list is the order the engine returns it.

== Set up the data

The schema below is the usual customers, orders and products. `Order.customer` is a link property, and the `Placed` and `Contains` edges are the same relationships stored as edges. A real application picks one form per relationship; this page uses both so that each pattern can show its form.

[source,python,subs="attributes+"]
----
{import-stmt}


def rows(language, query):
    for record in db.query(language, query):
        print(record.to_dict())


with arcadedb.create_database("./shop") as db:
    db.command("sql", "CREATE VERTEX TYPE Customer")
    db.command("sql", "CREATE VERTEX TYPE Product")
    db.command("sql", "CREATE VERTEX TYPE Order")
    db.command("sql", "CREATE PROPERTY Order.customer LINK OF Customer")
    db.command("sql", "CREATE EDGE TYPE Placed")
    db.command("sql", "CREATE EDGE TYPE Contains")
    db.command("sql", "CREATE VERTEX TYPE Person")
    db.command("sql", "CREATE EDGE TYPE Follows")

    with db.transaction():
        for name in ("Alice", "Bob", "Carol"):
            db.command("sql", "INSERT INTO Customer SET name = ?", name)
        for name, price in (("Widget", 5.0), ("Gadget", 12.5)):
            db.command("sql", "INSERT INTO Product SET name = ?, price = ?", name, price)
        for oid, cust, total in ((1, "Alice", 17.5), (2, "Alice", 5.0), (3, "Bob", 12.5)):
            db.command("sql", "INSERT INTO Order SET id = ?, total = ?, "
                       "customer = (SELECT FROM Customer WHERE name = ?)", oid, total, cust)
            db.command("sql", "CREATE EDGE Placed FROM (SELECT FROM Customer WHERE name = ?) "
                       "TO (SELECT FROM Order WHERE id = ?)", cust, oid)
        for oid, prod, qty in ((1, "Widget", 1), (1, "Gadget", 1), (2, "Widget", 1), (3, "Gadget", 1)):
            db.command("sql", "CREATE EDGE Contains FROM (SELECT FROM Order WHERE id = ?) "
                       "TO (SELECT FROM Product WHERE name = ?) SET qty = ?", oid, prod, qty)
        for n in ("Ann", "Ben", "Cy", "Di"):
            db.command("sql", "INSERT INTO Person SET name = ?", n)
        for a, b in (("Ann", "Ben"), ("Ben", "Cy"), ("Cy", "Di")):
            db.command("sql", "CREATE EDGE Follows FROM (SELECT FROM Person WHERE name = ?) "
                       "TO (SELECT FROM Person WHERE name = ?)", a, b)

    # ... the patterns below run here, inside the `with` block
----

NOTE: The `rows()` helper is only for printing. The query strings are the part to copy.

== Pattern 1: many-to-one, a foreign key

In Postgres:

[source,sql]
----
SELECT o.id, o.total, c.name AS customer
FROM orders o JOIN customers c ON c.id = o.customer_id
ORDER BY o.id;
----

In ArcadeDB the order holds a link to its customer, and you read through the link:

[source,python]
----
rows("sql", "SELECT id, total, customer.name AS customer FROM Order ORDER BY id")
----

[source,text]
----
{'id': 1, 'total': 17.5, 'customer': 'Alice'}
{'id': 2, 'total': 5.0, 'customer': 'Alice'}
{'id': 3, 'total': 12.5, 'customer': 'Bob'}
----

There is no join to plan and no `customer_id` to keep in step with a key: the link is the relationship. Inserting an order takes the customer as a subquery, as the setup shows: `customer = (SELECT FROM Customer WHERE name = ?)`. openCypher reads relationships as edges, so for the same answer there use the `Placed` edge, as in pattern 2.

== Pattern 2: one-to-many, the other way round

In Postgres:

[source,sql]
----
SELECT c.name, o.id AS order_id
FROM customers c JOIN orders o ON o.customer_id = c.id
ORDER BY o.id;
----

ArcadeDB SQL has two forms. `out('Placed')` follows the edge from each customer to its orders; `MATCH` writes the pattern:

[source,python]
----
rows("sql", "SELECT name, out('Placed').id AS order_ids FROM Customer ORDER BY name")
rows("sql", "MATCH {type: Customer, as: c}-Placed->{type: Order, as: o} "
            "RETURN c.name AS customer, o.id AS order_id ORDER BY order_id")
rows("opencypher", "MATCH (c:Customer)-[:Placed]->(o:Order) "
                   "RETURN c.name AS customer, o.id AS order_id ORDER BY order_id")
----

[source,text]
----
{'name': 'Alice', 'order_ids': [2, 1]}
{'name': 'Bob', 'order_ids': [3]}
{'name': 'Carol', 'order_ids': []}
{'customer': 'Alice', 'order_id': 1}
{'customer': 'Alice', 'order_id': 2}
{'customer': 'Bob', 'order_id': 3}
{'customer': 'Alice', 'order_id': 1}
{'customer': 'Alice', 'order_id': 2}
{'customer': 'Bob', 'order_id': 3}
----

The first query returns one row per customer with a list, so Carol, who has no orders, still appears. That is closer to a `LEFT JOIN` with `array_agg` than to the join above. The `MATCH` forms return one row per pair, like the join.

== Pattern 3: a join table becomes an edge with properties

In Postgres `order_items` joins orders to products and holds the quantity:

[source,sql]
----
SELECT oi.order_id, p.name AS product, oi.qty
FROM order_items oi JOIN products p ON p.id = oi.product_id
ORDER BY oi.order_id, p.name;
----

In ArcadeDB the `Contains` edge is that row. It points from the order to the product, and `qty` is a property of the edge. Query the edge type directly, and use `outV()` and `inV()` for its two ends:

[source,python]
----
rows("sql", "SELECT outV().id AS order_id, inV().name AS product, qty FROM Contains "
            "ORDER BY order_id, product")
rows("opencypher", "MATCH (o:Order)-[r:Contains]->(p:Product) "
                   "RETURN o.id AS order_id, p.name AS product, r.qty AS qty ORDER BY order_id, product")
----

[source,text]
----
{'order_id': 1, 'product': 'Gadget', 'qty': 1}
{'order_id': 1, 'product': 'Widget', 'qty': 1}
{'order_id': 2, 'product': 'Widget', 'qty': 1}
{'order_id': 3, 'product': 'Gadget', 'qty': 1}
{'order_id': 1, 'product': 'Gadget', 'qty': 1}
{'order_id': 1, 'product': 'Widget', 'qty': 1}
{'order_id': 2, 'product': 'Widget', 'qty': 1}
{'order_id': 3, 'product': 'Gadget', 'qty': 1}
----

NOTE: `out.id` does not work here: in the edge record `out` is the raw link, and the call `outV()` is what reads the vertex behind it. The SQL query returned `None` for both columns until it used `outV()` and `inV()`.

== Pattern 4: rows with no match, the anti-join

In Postgres:

[source,sql]
----
SELECT c.name FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
----

[source,python]
----
rows("sql", "SELECT name FROM Customer WHERE out('Placed').size() = 0")
rows("opencypher", "MATCH (c:Customer) WHERE NOT (c)-[:Placed]->() RETURN c.name AS name")
----

[source,text]
----
{'name': 'Carol'}
{'name': 'Carol'}
----

== Pattern 5: aggregate across a join

In Postgres:

[source,sql]
----
SELECT c.name AS customer, sum(o.total) AS spent
FROM customers c JOIN orders o ON o.customer_id = c.id
GROUP BY c.name ORDER BY c.name;
----

Group by the linked value. In SQL, `customer.name` reads through the link property; in openCypher you match the edge:

[source,python]
----
rows("sql", "SELECT customer.name AS customer, sum(total) AS spent FROM Order "
            "GROUP BY customer.name ORDER BY customer")
rows("opencypher", "MATCH (c:Customer)-[:Placed]->(o:Order) "
                   "RETURN c.name AS customer, sum(o.total) AS spent ORDER BY customer")
----

[source,text]
----
{'customer': 'Alice', 'spent': 22.5}
{'customer': 'Bob', 'spent': 12.5}
{'customer': 'Alice', 'spent': 22.5}
{'customer': 'Bob', 'spent': 12.5}
----

A subquery covers the semi-join, the `WHERE id IN (SELECT ...)` form. This one finds the customers who ordered a Widget:

[source,python]
----
rows("sql", "SELECT name FROM Customer WHERE @rid IN "
            "(SELECT customer FROM Order WHERE out('Contains').name CONTAINS 'Widget')")
----

[source,text]
----
{'name': 'Alice'}
----

== Pattern 6: a self-join of any depth

In Postgres, "who does Ann follow, directly or through one more person" is a self-join or a recursive CTE:

[source,sql]
----
WITH RECURSIVE reach(id, depth) AS (
  SELECT followee_id, 1 FROM follows WHERE follower_id = (SELECT id FROM people WHERE name = 'Ann')
  UNION ALL
  SELECT f.followee_id, r.depth + 1 FROM follows f JOIN reach r ON f.follower_id = r.id WHERE r.depth < 2
)
SELECT p.name FROM reach r JOIN people p ON p.id = r.id;
----

In ArcadeDB the depth is a parameter of the walk:

[source,python]
----
rows("sql", "SELECT name FROM (TRAVERSE out('Follows') FROM "
            "(SELECT FROM Person WHERE name = 'Ann') MAXDEPTH 2) WHERE $depth > 0")
rows("sql", "MATCH {type: Person, as: a, where: (name = 'Ann')}"
            ".out('Follows'){as: b, while: ($depth < 2), where: ($depth > 0)} RETURN b.name AS name")
rows("opencypher", "MATCH (a:Person {name: 'Ann'})-[:Follows*1..2]->(b:Person) "
                   "RETURN b.name AS name ORDER BY name")
----

[source,text]
----
{'name': 'Ben'}
{'name': 'Cy'}
{'name': 'Ben'}
{'name': 'Cy'}
{'name': 'Ben'}
{'name': 'Cy'}
----

`TRAVERSE` includes the start record at depth 0, which is why the first query filters on `$depth > 0`.

== What a JOIN does here

[source,python]
----
db.query("sql", "SELECT c.name, o.id FROM Customer c JOIN Order o ON o.customer = c.@rid")
----

[source,text]
----
ArcadeDBError Query failed: com.arcadedb.exception.CommandSQLParsingException: SQL syntax error at line 1, column 36: mismatched input 'JOIN' expecting {<EOF>, ';'}
SELECT c.name, o.id FROM Customer c JOIN Order o ON o.customer = c.@rid
                                    ^
----

== What does not translate

* *`JOIN` in any form.* The keyword is a syntax error. Rewrite each join as one of the patterns above.
* *ORMs such as SQLAlchemy.* They generate `JOIN` queries, which this dialect does not parse. Use `db.query` and `db.command` with the statements on this page.
* *BI tools and anything else that writes joins for you.* Tools that build `JOIN ... ON` queries from a schema, over a driver or a wire protocol, generate SQL that fails the same way, because the dialect has no `JOIN` to emit. Write the queries by hand, as above.
* *A foreign key as a declared constraint.* A link property holds a record ID and is followed on read. This page does not cover whether the database checks it on write.

If your queries are mostly relationships, start with openCypher: it is the shorter language for them, and the patterns above show each one.
