= Where the logs go
:description: Where the engine writes its log file on the arcadedb and arcadedb-jvm packages, how to move it, when it also logs to the console, and what the packages never write.

Neither package writes a `log` directory into your working directory. The engine's own default is `./log/arcadedb.log`, relative to wherever the process started. Both packages replace it with a per-user directory, so a read-only working directory or a notebook that starts anywhere leaves no files behind.

== Default location

The log directory is `arcadedb/log` under your state directory:

[cols="1,3"]
|===
| Platform | Directory

| Linux
| `$XDG_STATE_HOME/arcadedb/log`, or `~/.local/state/arcadedb/log` when `XDG_STATE_HOME` is not set to an absolute path

| macOS
| `~/Library/Logs/arcadedb/log`

| Windows
| `%LOCALAPPDATA%\arcadedb\log`
|===

When the directory cannot be created or written, the package logs a warning and uses a new `arcadedb-log-*` directory under the system temp directory.

The directory holds the engine log (`arcadedb.log.0`, `arcadedb.log.1` and so on, up to 10 files of 100 MB), and the logging configuration that the package writes for the engine (`logging.properties`, or `logging-file-only.properties` when the console is off, see below). The `arcadedb-jvm` package also keeps the JVM crash file `hs_err_pid<pid>.log` there.

== Console output

The engine logs to its file and, on Linux and macOS, to the console too (stderr). On Windows the console log is off by default: the log goes to the file only.

The reason is a Windows detail. The runtime saves the OS handle of stdout and stderr when it starts. If your program redirects file descriptor 1 or 2 later (pytest's default output capture does this around every test, and so can a service or an application that embeds the library), Windows closes that handle and can give the same handle value to the next file that is opened, for example a database file. The next console log line is then written into that database file and corrupts it. The log file does not have this problem, because the engine opens it itself.

Set `ARCADEDB_LOG_CONSOLE` before the first database is opened to choose on any platform:

[source,bash]
----
export ARCADEDB_LOG_CONSOLE=1   # also log to the console (Windows: only if your program never redirects fd 1 or 2)
export ARCADEDB_LOG_CONSOLE=0   # log to the file only (also on Linux and macOS)
----

`1`, `true`, `yes` and `on` turn the console log on, `0`, `false`, `no` and `off` turn it off. Any other value, and no value, gives the platform default above. The package writes the configuration without the console handler to `logging-file-only.properties` in the log directory, so processes with different settings that share a directory do not replace each other's file.

A `java.util.logging.config.file` that you set yourself (see below) replaces all of this: its handlers decide where the log goes.

Log lines are not the only text the runtime writes through that handle: a warning the runtime or a library prints, or a printed stack trace, goes to Java's `System.out` or `System.err`. In the `arcadedb-jvm` package, with the console off (the default on Windows, or `ARCADEDB_LOG_CONSOLE=0`), the package therefore points `System.out` and `System.err` at `arcadedb-stdio.log` in the log directory, a file that it opens itself, right after the JVM starts. The runtime's own start-up warning (`WARNING: Using incubator modules: jdk.incubator.vector`) is printed while the JVM is created, before the package can do this, and still goes to the stderr of your process. With `ARCADEDB_LOG_CONSOLE=1` on Windows, `System.out` and `System.err` keep the runtime's handle, so the risk above stays: do not redirect fd 1 or 2 after the first database is opened.

The packages themselves never print to the console on Windows: the glue code of the native build logs through the same engine log instead of writing to stderr.

== Choose the directory

Set `ARCADEDB_LOG_DIR` before the first database is opened. The first call that starts the engine reads it, so setting it later has no effect in the same process.

[source,bash]
----
export ARCADEDB_LOG_DIR=/var/log/my-app/arcadedb
----

== Settings that win over `ARCADEDB_LOG_DIR`

The packages pass two Java system properties to the engine: `arcadedb.server.logsDirectory` (the directory) and `java.util.logging.config.file` (the `logging.properties` in it). If you set one of them yourself, yours is kept and the other default still applies.

`arcadedb-jvm`:: Add the property to `jvm_kwargs={"jvm_args": [...]}` or to the environment variable `ARCADEDB_JVM_ARGS`, for example `-Darcadedb.server.logsDirectory=/var/log/arcadedb`.

`arcadedb` (native):: Add the property to the environment variable `ARCADEDB_NATIVE_ISOLATE_ARGS`. It takes space-separated isolate arguments, so a directory in it cannot contain a space. For example `ARCADEDB_NATIVE_ISOLATE_ARGS=-Darcadedb.server.logsDirectory=/var/log/arcadedb`. Use `ARCADEDB_LOG_DIR` for a directory with a space in its name.
