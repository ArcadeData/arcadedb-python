= Continuous integration
:description: Which platforms and Python versions the CI runs for a pull request, and which for main, the nightly run and a release.

Two workflows test the `arcadedb-jvm` package: `test-python-bindings.yml` builds a wheel and runs the unit tests, and `test-python-examples.yml` runs the scripts in `examples/`. Both build the wheels on a native runner of each platform. A third workflow, `native.yml`, builds and tests the `arcadedb` (native) package; see <<_native_build,Native build>>.

The package supports four platforms and four Python versions (3.11 to 3.14). That is 16 combinations for each workflow. A pull request does not run all of them, because the organisation shares one runner limit with ArcadeData/arcadedb. Each macOS or Windows job on a pull request delays the upstream jobs too.

== What runs when

The script `scripts/select_matrix.py` chooses the combinations. The first job of each workflow, `Download ArcadeDB JARs`, runs it and passes the result to the test job.

[cols="2,3,3"]
|===
| Event | Unit tests (`Test arcadedb`) | Examples (`Test Python Examples`)

| Pull request
| `linux/amd64` on all four Python versions. `linux/arm64`, `darwin/arm64` and `windows/amd64` on Python 3.11 and 3.14.
| All four platforms on Python 3.14.

| Push to `main`, the nightly run, a manual run, a release
| All 16 combinations.
| All 16 combinations.
|===

A pull request runs 20 checks: 14 test jobs (10 and 4), the two `Download ArcadeDB JARs` jobs, the two summary jobs, `Bandit security scan` and `Dependency floor audit`. The full matrix runs 38.

The names of the test jobs do not change: `Test arcadedb (<platform>, Python <version>)`. A check keeps its history when a pull request runs fewer of them.

A release always runs the full matrix, because `release.yml` expects one wheel for each platform and Python version. The nightly run also tests against the newest `arcadedata/arcadedb:latest` image.

== Other rules

* A pull request that changes only documentation (`docs/**`, `*.adoc`, `CLAUDE.md`, `examples/README.md`, `LICENSE*`) runs nothing.
* A draft pull request skips the platform jobs. Marking it ready for review starts them.
* A new push to a pull request cancels the run it replaces. A run on `main` is never cancelled.

== Native build

The workflow `native.yml` builds the native image of the `arcadedb` package. It does not follow the table above.

* A pull request runs it only when native paths change: `native/**`, `src/arcadedb/_native/**`, the native tests, or `native.yml` itself. It then runs on `linux-x86_64` with Python 3.12 only.
* A push to `main`, the nightly run, a manual run (dispatch) and a release tag run the full platform matrix: `linux-x86_64`, `linux-aarch64`, `macos-arm64` and `windows-x64`.
* A native image build takes about 1 to 2.5 hours for each platform. The organisation shares one runner limit with upstream ArcadeDB, so do not add runs lightly. Change the paths or the matrix of `native.yml` only for a reason that you can write down.

== Change the selection

Edit `PULL_REQUEST_LEGS` in `scripts/select_matrix.py`. The test `tests/test_select_matrix.py` fixes the full matrix at 16 combinations, so a change that shrinks it fails. When you add a Python version, add it to `PYTHONS` in the script and to the classifiers in `pyproject.toml`. A test checks that both lists are the same, and that `requires-python` is the oldest of them. When you drop one, remove it from the same places and update the counts in the test.
